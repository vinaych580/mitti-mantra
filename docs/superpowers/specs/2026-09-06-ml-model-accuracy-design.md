# ML Model Accuracy — Crop Recommendation & Yield Prediction — Design Spec

**Date:** 2026-09-06
**Status:** Approved for planning
**Author:** Claude (session with support.vr7@gmail.com)

## 1. Summary

The crop-recommendation classifier and yield regressor in `ml/` both report
metrics that are either bad or untrustworthy. Diagnosis (not guesswork —
figures below are measured against the real persisted holdout sets) found
the root cause is not the algorithm, it's how each model's training labels
are generated, plus a second pipeline (`ml/evaluate_models.py`) that silently
overwrites the same production model files using a materially different,
easier synthetic dataset. This spec fixes the label generation for both
models, unifies the two pipelines so accuracy numbers are trustworthy, and
then runs a fair algorithm comparison to pick what actually gets deployed.

## 2. Why

Measured against `ml/models/holdout_recommend.joblib` /
`holdout_yield.joblib` (the genuinely-unseen rows persisted at training
time — see `AUDIT_REPORT.md` B-2/C-3 for why these, not a freshly-rebuilt
split, are the trustworthy thing to evaluate against):

- **Crop recommendation: F1-macro 0.117, and 21 of 32 crops score exactly
  0.00 F1** — rice, wheat, maize, cotton, soybean, sunflower, tomato,
  potato, onion, sugarcane, mango, groundnut, jowar, moong, arhar, bajra,
  mustard, barley, chilli, jute, tobacco, and paddy_basmati are *never*
  correctly recommended. Only cashew, coconut, banana, ragi, pulses, tea,
  and turmeric are ever predicted; cashew alone accounts for 38% of all
  training labels.
- **Root cause, traced in `ml/train_models.py::_build_recommendation_dataset`:**
  labels are generated by ranking crops on `roi_percent * budget_fit` alone
  — a formula that structurally favors low-input-cost crops (ragi, pulses:
  ₹12–17k/acre) and high price-to-cost-ratio perennials (cashew, coconut:
  eligible in *every* seasonal sampling round, not just one, since
  "perennial"/"annual" crops pass the season-eligibility check regardless of
  which season is being sampled). It has no risk, soil-fit, or confidence
  term at all. This is a materially different (and cruder) formula than
  the one the product actually uses to rank crops for a farmer
  (`_score_single_crop`'s `smart_score` in `ml/predict.py`:
  `0.35·roi + 0.20·risk_confidence + 0.15·budget_fit + 0.15·soil_health +
  0.15·ml_term`, each term clamped/normalized to a comparable 0–100 scale).
  The classifier is being trained to reproduce a proxy that isn't what
  "good recommendation" means anywhere else in this codebase.
- **This isn't just a training-time number — it's live.** `smart_score`
  blends this classifier's `predict_proba` back in as `ml_term` (15%
  weight). A farmer asking about wheat or rice today gets that 15% slice
  computed from a model that has no evidence those crops can ever be
  right, because its labels never included them.
- **Yield: 321.6% MAPE is real but overstated.** 61% of the held-out set
  is the deliberately-tiny synthetic "climate mismatch" rows injected by
  `_build_yield_dataset` (`mismatched_yield = base_yield * climate_factor *
  0.1`), whose percentage errors are mathematically explosive against a
  near-zero denominator. Excluding them, MAPE is 113.6% — still high enough
  to represent a real gap, but the headline number today conflates "a
  metric artifact from rows deliberately designed to be near-zero" with
  "the model is bad at predicting real yields," and nobody can tell which
  from `audit_metrics.json` alone.
- **`ml/evaluate_models.py` makes both problems worse, silently.** It
  benchmarks RandomForest against CatBoost/XGBoost/LightGBM and reports
  96%/0.84-F1-macro for recommendation and 0.99 R² for yield — but its
  `_build_recommendation_dataset` uses `profit` (not ROI), the exact
  raw-profit-dominance formula `train_models.py`'s own comments (FIX C-1)
  say was already found and replaced for this same bias; and its
  `_build_yield_dataset` doesn't inject the climate-mismatch rows at all.
  Both benchmarks are measured on a strictly easier, non-equivalent
  dataset — not a better model. And critically, `evaluate_crop_recommendation()`
  /`evaluate_yield_prediction()` call `joblib.dump(..., MODEL_DIR /
  "recommend_model.joblib")` / `"yield_model.joblib"` directly — the *same*
  filenames `ml/train_models.py` (wired to `POST /api/ml/train`) writes.
  Running the "evaluation" script by hand silently redeploys a model
  trained on the easier dataset, with no manifest/hash update and no audit
  refresh. `evaluation_manifest.json` is already ~92hr-stale evidence this
  has happened before (see `AUDIT_REPORT.md` B-1).

## 3. Users & Success Criteria

- **Primary:** every caller of the recommendation/yield subsystem —
  `/api/recommend`, `/api/crop`, `/api/yield`, `/api/rotation-plan`,
  `/api/optimal-mix`, `/api/crop-comparison`, and the chatbot's recommend/
  yield intents — anywhere `ml/predict.py` consults `recommend_model` or
  `yield_model`.
- **Out of scope:** the price-forecasting model and disease CNN are not
  touched (both already measure reasonably healthy: price R²=0.91, disease
  80.4% accuracy) — see §4.

Success is measured, not assumed, against the baseline numbers in §2 after
retraining on the corrected pipeline:

- No crop that is a genuinely plausible recommendation somewhere in the
  sampled budget/soil/weather range — in particular the current zero-F1
  staples rice, wheat, maize, cotton, and soybean — should remain
  structurally unrecommendable. F1-macro should rise substantially from
  0.117. (This is deliberately not phrased as "all 32 crops get non-zero
  F1": a crop that is genuinely never ROI-competitive in this dataset's
  budget range, e.g. coffee at ₹180k/acre input cost, legitimately
  earning near-zero representation is correct behavior, not a bug — §7.3
  is how this gets told apart from the bug this spec fixes.)
- Yield MAPE is reported split by row provenance (real-history-derived vs.
  synthetic climate-mismatch), and the real-rows MAPE (baseline: 113.6%)
  should materially improve. R² (0.8115) and drought-robustness R²
  (0.6699) should not regress, and are expected to improve.
- `evaluate_models.py` can be run at any time without altering what's
  deployed — its only side effect is `evaluation_manifest.json`.
- Whichever algorithm is actually deployed for each model was chosen by a
  fair comparison on the same dataset the deployed model is trained on —
  not a different, easier one.

## 4. Scope

**In scope:**
- `ml/dataset_builders.py` (new): the shared, corrected dataset-construction
  code for both models, used by training, evaluation, and (where relevant)
  auditing alike.
- `utils/calculations.py`: extract `compute_smart_score()` as a pure
  function (see §6.1).
- `ml/predict.py`: `_score_single_crop` calls the extracted function instead
  of inlining the formula. No behavior change to production scoring.
- `ml/train_models.py`: imports dataset builders from the new shared module;
  recommendation labels generated from the corrected, smart-score-aligned
  formula; whichever algorithm wins §8's bake-off is wired in here.
- `ml/evaluate_models.py`: refactored to import the shared dataset builders
  and to stop writing `ml/models/*.joblib`/`*_encoders.joblib` — becomes a
  read-only comparison tool whose only output is `evaluation_manifest.json`.
- `ml/audit_models.py`: adds per-class precision/recall/F1 for
  recommendation, and a real-vs-synthetic MAPE split for yield.
- `requirements.txt`: gains the winning algorithm's dependency if it isn't
  RandomForest (with a documented bundle-size note — see §9).
- New/extended tests under `tests/`.

**Out of scope (explicitly deferred):**
- Price forecasting and the disease CNN (user-scoped to recommendation +
  yield; both already measure reasonably healthy).
- Reconsidering whether the recommendation classifier should exist at all,
  or shrinking `ml_term`'s 15% weight in production `smart_score`. Raised
  during brainstorming as "Approach C": since the classifier's ground truth
  is entirely formula-derived, a perfect classifier can only ever tie the
  formula, never beat it. That's a real architectural question but a
  different one from "improve accuracy" — left for the user to decide on
  separately.
- Sourcing new real-world ground-truth data. This fix works within the
  existing synthetic-simulation paradigm (correcting its internal
  consistency), not replacing simulation with real outcomes data, none of
  which exists for crop recommendation.
- Rebalancing season-eligibility sampling exposure (perennial/multi-season
  crops currently get evaluated in every seasonal round, season-locked
  crops in only one). This is a real, secondary contributor (§2), but the
  primary fix — aligning the score formula itself — is expected to
  substantially reduce its effect on its own. Re-measure after §6/§7; only
  build explicit exposure-balancing as a follow-up if skew toward
  multi-season crops still looks structural, not as a pre-emptive change
  here (deliberately not committing to a fix for a problem not yet
  confirmed to survive the formula correction).
- Vercel bundle-size remediation. §9 measures and reports the delta if a
  new algorithm is promoted; actually fixing deployment/bundling (already
  flagged and left open as B-14 in `AUDIT_REPORT.md`) is a separate
  decision for the user.
- Any change to the regional-saturation commit log or `/api/commit-crop`
  (shipped immediately prior to this spec). Saturation is a real-time,
  live-commitment-log signal with no meaning for a synthetic what-if
  sample — see §6.2, it's simply passed as absent (zero penalty) during
  label generation, matching its real behavior for any region/crop/season
  combination nobody has committed to yet.

## 6. Design — Fixing the Recommendation Labels

### 6.1 `compute_smart_score()` — one formula, not two

Extract `ml/predict.py:1201-1210`'s weighted blend into
`utils/calculations.py` (alongside `calculate_climate_factor` and friends,
which it already calls into):

```python
def compute_smart_score(
    roi_normalized: float,
    confidence_score: float,
    budget_fit: float,
    soil_health: float,
    ml_term: float,
    saturation_penalty: float = 0.0,
) -> float:
    return clamp(
        0.35 * roi_normalized
        + 0.20 * confidence_score
        + 0.15 * budget_fit
        + 0.15 * soil_health
        + 0.15 * ml_term
        - saturation_penalty * 0.25,
        0.0, 100.0,
    )
```

`_score_single_crop` calls this instead of inlining the formula — a
behavior-preserving refactor for production. `ml/dataset_builders.py`'s
label generator calls the *same* function. The five weights can no longer
silently drift apart between "how a farmer's request is actually scored"
and "what a training label says the best crop is," because there is only
one place they're written down.

This is deliberately narrower than making the label generator call
`_score_single_crop` itself: that function also pulls in batched ML-yield
lookups, cached live mandi prices, and the region-saturation dict — all
meaningful for a real request, none of them meaningful for a synthetic
what-if sample. §6.2 covers how each of `compute_smart_score`'s five inputs
is supplied during label generation instead.

### 6.2 Supplying `compute_smart_score`'s inputs during label generation

For each synthetic sample (region, season, budget, irrigation, ph, rainfall,
temp — same sampling as today) and each eligible crop:

| Input | Source during label generation |
|---|---|
| `roi_normalized` | `clamp(roi_percent / 3.0, 0.0, 100.0)` — same formula as production, fed by the same `calculate_climate_factor`/`calculate_soil_factor`-based yield estimate and profit calc already used today |
| `confidence_score` | `calculate_risk_score_and_subscores(...)`'s output, called directly (same function `smart_risk_score` wraps in production) — **new**, not used by today's label formula at all |
| `budget_fit` | same formula as production, already computed today |
| `soil_health` | the same n/p/k-ratio formula `_score_single_crop` uses — **new**, today's label formula only feeds soil ph/N into `calculate_soil_factor`'s yield-multiplier, not this separate ratio term |
| `ml_term` | **forced to equal `roi_normalized`** (production's own fallback value when no recommend_model is loaded — see below) |
| `saturation_penalty` | **forced to `0.0`** (no commitment-log data exists for a synthetic scenario — equivalent to production's real "no baseline for this region/crop/season yet" case) |

**Why `ml_term` is forced, not computed from whatever model happens to be
loaded:** production's `ml_term` already falls back to `roi_normalized`
when `_ml_recommend_model is None`. Using the *live* model's `predict_proba`
during label generation would make training circular — the classifier
would be partly trained on its own prior predictions, with results
depending on incidental process state (whether a previous model happens to
be loaded when `train_models.py` runs). Forcing the fallback branch during
label generation breaks that circularity outright: labels reflect only the
four deterministic components, and at inference time the trained model's
`predict_proba` becomes a genuine, independent 15%-weight signal on top —
not something it was ever asked to reproduce.

### 6.3 Label assignment: argmax, not softmax-sampling

Today's softmax-with-temperature=15 sampling (`train_models.py` FIX C-1)
was a workaround for the *old* unbounded `roi_percent * budget_fit` scale,
where strict argmax left ~20 crops with zero label representation. Once
labels come from `compute_smart_score`'s clamped 0–100 scale — the same
scale, same function, `recommend_crops()` uses to rank and return crops to
a real farmer — argmax is the semantically correct choice: it's exactly
what "the top recommendation" already means everywhere else in this
codebase, and it removes an arbitrary hyperparameter tuned for a formula
this spec is replacing.

This is a prediction, not a guarantee. Regenerate the dataset, rerun the
same per-class F1 diagnostic behind §2's numbers, and check specifically
whether rice/wheat/maize/cotton/soybean move off zero. If some crop is
still structurally at ~0% representation, determine from the same
diagnostic whether that's a genuine "never ROI-competitive in this budget
range" result (acceptable — §3) or a residual formula/sampling artifact
(not acceptable — reintroduce softmax noise, retuned for the 0–100 scale,
as a follow-up). Don't pre-build that fallback speculatively before
confirming it's still needed.

## 7. Design — Yield Metric Honesty

### 7.1 Tag row provenance in the dataset builder

`ml/dataset_builders.py::_build_yield_dataset` returns an additional
per-row `source` array alongside `X`/`y`: `"real"` for rows built directly
from `yield_history.csv`, `"augmented"` for the ±10% noise-perturbed
copies, `"synthetic_mismatch"` for the injected climate-mismatch rows.
`_save_holdout` persists this alongside `X_test`/`y_test` in
`holdout_yield.joblib` so provenance survives into the audit step exactly,
rather than being reconstructed later by guessing from `y` magnitude.

### 7.2 Split reporting in `ml/audit_models.py`

Report (and log) MAPE, MAE, RMSE separately for the `"real"`+`"augmented"`
subset vs. the full set including `"synthetic_mismatch"` rows. The
real-rows number becomes the one tracked for regressions; the full-set
number stays available for anyone checking the model's behavior on the
deliberately-adversarial climate-mismatch scenarios it was also trained on.

### 7.3 What's actually being fixed vs. just measured

Splitting the metric doesn't, by itself, close the 113.6%-on-real-rows gap
— that requires the §8 bake-off (better algorithm/hyperparameters on the
same, now-honestly-measured, real-history data). This section exists so
that gap is visible and trackable at all; today it's invisible, averaged
together with rows that were never meant to resemble realistic yields.

## 8. Design — One Dataset Builder, Then a Fair Bake-off

1. Move `_build_yield_dataset`, `_build_recommendation_dataset`,
   `_fit_label_encoders`, `_row_hash`, `_save_holdout`, `ALL_SEASONS`, and
   `make_crop_param`/`_yield_features` into `ml/dataset_builders.py`,
   incorporating §6 and §7.1's fixes. This is the *only* place either
   dataset is built.
2. `ml/train_models.py` imports from `ml/dataset_builders.py` instead of
   defining its own copies (removes ~250 lines of now-duplicate code).
3. `ml/evaluate_models.py` imports the same module instead of its own
   drifted copies, and **stops calling `joblib.dump()` on
   `recommend_model.joblib`/`yield_model.joblib`/`*_encoders.joblib`**. Its
   `run_pipeline()` writes only `evaluation_manifest.json`. This is the
   concrete fix for §2's "both pipelines write the same files" finding —
   after this change, running `python -m ml.evaluate_models` by hand can no
   longer change what's deployed.
4. Run the (now-fair, now-single-dataset) bake-off: RandomForest vs.
   whichever of CatBoost/XGBoost/LightGBM are installed, exactly as
   `evaluate_models.py` already does, but on the corrected data. Decision
   metric for recommendation is **F1-macro**, not raw accuracy — given the
   class-imbalance history here, accuracy alone would repeat §2's mistake
   of rewarding a model that nails a few dominant classes while ignoring
   the rest.
5. **Promotion is a deliberate code change, not a script side effect.**
   Whichever algorithm wins gets its constructor + tuned hyperparameters
   (from the existing `RandomizedSearchCV` step) written into
   `train_recommendation_model()` / `train_yield_model()` in
   `ml/train_models.py`, in a normal reviewed commit — same as any other
   change to what gets deployed via `POST /api/ml/train`.

## 9. Consequence: Production Dependencies & Bundle Size

If the winning algorithm isn't `RandomForestClassifier`/`RandomForestRegressor`,
its package moves from `requirements-dev.txt` (currently guarded behind a
`try/except CATBOOST_AVAILABLE`-style optional import) into `requirements.txt`
as a hard production dependency, following this repo's existing
comment-the-why convention in that file.

`AUDIT_REPORT.md` (B-14) already flags `recommend_model.joblib` at 82.5MB
against Vercel's bundle constraints. This spec does not fix that
constraint, but the implementation must measure and report the new
model's serialized size and the new dependency's installed size as part of
promotion (§8.5), so the tradeoff is visible before merge — not discovered
after a deploy fails. If the winning model is *larger*, that's a decision
for the user at promotion time, not something to route around silently.

## 10. Testing

- `_build_recommendation_dataset` (new module): assert that
  rice/wheat/maize/cotton/soybean each appear as the argmax label at least
  once across a fixed-seed sample — the concrete regression test for §2's
  bug.
- `compute_smart_score`: a shared-fixture test asserting `_score_single_crop`
  and the dataset-builder's label generator produce byte-identical scores
  given the same five inputs — guards §6.1's "can't drift apart again"
  property directly, not just by convention.
- `ml/evaluate_models.py`: run its pipeline against a tmp `MODEL_DIR` and
  assert `recommend_model.joblib` / `yield_model.joblib` /
  `*_encoders.joblib` are **not** written or modified — the regression
  test for §2's file-clobbering bug.
- Yield provenance split: a fixture dataset with known real/augmented/
  synthetic-mismatch row counts; assert `audit_models.py`'s split MAPE
  matches a hand-computed expectation.
- Full retrain + audit as a manual/CI step: `python -m ml.train_models`,
  inspect refreshed `audit_metrics.json` for per-class F1 (staples off
  zero) and split yield MAPE, confirm `manifest.json`'s model hashes
  changed.
- Manual spot-check: request `/api/recommend` for a rabi-season, wheat-
  favorable region/budget and confirm wheat now appears as a plausible
  candidate rather than being structurally absent — the same "Smart
  recommend" dashboard card touched by the immediately-prior regional-
  saturation feature.

## 11. Explicitly Deferred (not this build)

- Everything listed as out-of-scope in §4.
- Retuning or reintroducing softmax-sampling noise for label generation
  (§6.3) — only if the empirical re-check shows it's still needed.
- Explicit season-eligibility exposure balancing (§4) — only if the
  empirical re-check shows multi-season crops are still structurally
  over-represented after the formula fix.

## 12. Known Limitations (accepted, not fixed in this build)

- **The recommendation model's ceiling is still its own label formula.**
  Even after this fix, the classifier's ground truth remains 100%
  simulation-derived (§4's Approach-C deferral) — there is no independent
  real-world signal (e.g., actual farmer outcomes) it could learn instead.
  This spec makes the simulation it learns from internally consistent with
  production scoring; it does not give the model access to anything the
  deterministic formula didn't already know. A perfectly-fit model after
  this change still only ties `compute_smart_score`'s deterministic
  components — it cannot exceed them.
- **Season-eligibility exposure asymmetry is measured, not eliminated,
  by this build** (§4, §11) — if it turns out to still matter after the
  formula fix, it's a follow-up.
- **Yield's real-rows MAPE may still be materially above a "good" bar
  even after the bake-off.** `yield_history.csv` has 566 real rows total
  spread across many crop/region/season combinations; some combinations
  are inherently thin. The bake-off can find a better algorithm/
  hyperparameters for the data that exists — it cannot manufacture more
  real historical coverage where none exists.
- **This build doesn't touch price forecasting or the disease CNN**
  (§4) — both were measured healthy during diagnosis, but neither
  received the same depth of scrutiny the two in-scope models did, since
  the user scoped this spec to recommendation + yield specifically.
